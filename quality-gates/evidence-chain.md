# 证据链规范

## 强制三元组

每个关键论断必须采用：

```
【论断】[一句话结论]
【论据】[支撑的事实/数据/逻辑]
【来源】[官方文档/RFC/书籍/案例 — URL 或路径]
【可信度】✅确定 / 🔶高度可能 / ⚠️推测
```

## 什么算"关键论断"

需要证据链的：
- 技术选型（"用 X 而不是 Y"）
- 性能/数据声明（"QPS 1000+"）
- 推荐结论（"推荐方案 A"）
- 风险评估（"X 概率失败"）
- 行业数据（"市场规模 N 亿"）
- 法律/医疗等专业声明

不需要的：
- 通用常识（"HTTP 是协议"）
- 个人偏好（"我倾向简洁风格"）
- 描述性事实（"代码长 50 行"）

## 可信度三档

### ✅ 确定
- 来自权威来源（官方文档、RFC、上市公司财报）
- 可被独立验证
- 引用近期数据（≤ 2 年）

### 🔶 高度可能
- 多个二手来源支持
- 行业普遍共识
- 基于已验证案例的推断

### ⚠️ 推测
- 缺乏直接证据
- 基于经验或常识
- 数据可能过时

每个 ⚠️ 推测必须主动建议用户验证。

## 来源等级（优先级）

```
1. 官方文档/规范（FastAPI Docs, RFC, ISO）
2. 官方课程（DeepLearning.AI, Coursera 认证）
3. 经过同行评议的论文
4. 上市公司财报/年报
5. 知名研究机构报告（McKinsey, Gartner）
6. 知名作者书籍
7. 知名工程博客
8. 一般技术博客
9. 论坛/StackOverflow
10. 个人推断
```

引用顺序：尽量从高等级来源取。

## 证据链格式示例

### 示例 1：技术选型
```
【论断】推荐使用 FastAPI
【论据】异步性能（vs Flask 同步）、自动 OpenAPI 文档、完整类型注解支持
【来源】FastAPI 官方文档 — https://fastapi.tiangolo.com/features/
【可信度】✅
```

### 示例 2：性能声明
```
【论断】PostgreSQL 单机可承受 10K QPS（OLTP 场景）
【论据】社区基准测试在 16C/32G 配置下达到 12K TPS
【来源】PostgreSQL 16 性能基准 — https://www.postgresql.org/docs/16/...
【可信度】🔶
```

### 示例 3：商业数据
```
【论断】中国咖啡市场年增长 15%
【论据】2024 年市场规模 X 亿，对比 2023 年增长
【来源】艾瑞咨询《2024 中国咖啡行业报告》
【可信度】🔶（注：数据为统计推算，实际数字可能有 ±2% 误差）
```

### 示例 4：推测
```
【论断】此方案上线后 6 个月内可达 ROI 平衡
【论据】参考类似方案的历史数据，基于乐观假设
【来源】3 个相似项目的复盘记录（内部）
【可信度】⚠️（建议监测前 3 个月数据后再做调整）
```

## 来源不可达时

如果引用的资源失效（404）：
1. 先尝试找替代来源
2. 找不到则降级可信度（✅ → 🔶）
3. 标注"原始来源已失效，备选：[新来源]"

## 证据链汇总表（在 deliver 中输出）

```
| # | 论断 | 来源 | 可信度 |
|---|------|------|--------|
| 1 | 推荐 FastAPI | https://fastapi.tiangolo.com/ | ✅ |
| 2 | QPS 10K | PostgreSQL 16 docs | 🔶 |
| ... |
```

## 反模式（绝对避免）

- ❌ "据说" / "听说" / "好像"
- ❌ "大家都用" / "行业都这样"
- ❌ "X 公司案例"（不给具体哪个公司）
- ❌ 编造数字（"市场规模 100 亿"无来源）
- ❌ 引用已失效链接不标注

## 整体可信度

deliver 的整体可信度 = max 中的最低档
- 全部 ✅ → 整体 ✅
- 含任一 🔶 → 整体 🔶
- 含任一 ⚠️ → 整体 ⚠️ + 建议用户验证
