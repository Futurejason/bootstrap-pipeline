## 概述

**Project Bootstrap Pipeline** 是一个企业级项目启动加速器与开发过程协同工具。

核心使命：将项目启动阶段的杂乱输入（需求沟通录音、各类技术文档、业务数据）转化为可直接驱动开发的结构化资产，并在开发过程中持续支撑变更管理与协同沟通。

**工作模式：两阶段迭代 + 开发阶段持续支撑**

```
输入 → 理解 → 发现缺口 → 生成澄清文档 → 用户拿去确认
  → 确认结果回来 → 更新 Solution_Context → 检查是否还有缺口
  → [循环] → 理解完整 → 生成开发资产
  → 开发中遇到问题 → 再次触发澄清循环
```

---

## 核心概念：Solution_Context

**Solution_Context** 是贯穿整个 Pipeline 的核心上下文容器，存储在 `docs/solution-context.json`。

它随每轮澄清循环持续积累和更新，是生成最终开发资产的**唯一依据**。

| 字段 | 说明 |
|------|------|
| `project_goal` | 项目目标（一句话描述） |
| `completeness_score` | 完整度评分（0-100，≥80 才能进入阶段二） |
| `stakeholders` | 相关方列表（角色、诉求、联系方式） |
| `confirmed_requirements` | 已确认的需求（含确认人和时间） |
| `open_questions` | 待确认的问题（含影响范围和优先级） |
| `constraints` | 已知约束（技术、业务、时间、资源） |
| `assumptions` | 当前假设（未确认但暂时采用的判断） |
| `decisions` | 已做决策记录（决策内容、依据、决策人） |
| `clarification_rounds` | 澄清轮次记录 |

**更新规则**：每次用户带回确认结果后立即更新，不得延迟。

## 铁律（任何阶段不可违反）

| 编号 | 规则 |
|------|------|
| INV-001 | 每个阶段完成后必须等待用户明确确认，不得自动推进 |
| INV-002 | 用户反馈问题时，AI 自行排查根本原因并修复，不得要求用户去排查 |
| INV-003 | 验收测试必须覆盖所有功能入口 + 异常场景 |
| INV-004 | 部署前必须读取所有配置文件，识别潜在问题 |
| INV-005 | 配置文件已存在时必须验证内容，不得跳过 |
| INV-006 | 文档、代码、配置三者必须保持一致 |
| INV-007 | 所有技术方案必须注明来源 |
| **INV-008** | **澄清文档必须达到可直接转发给上游需求方的质量，不需要用户二次加工** |
| **INV-009** | **Solution_Context 是生成开发资产的唯一依据，不得引入未经确认的假设** |
| **INV-010** | **Solution_Context 完整度 < 80 不得进入阶段二** |

## 阶段一：理解与澄清

### Phase 1 — 输入解析与初始理解
**角色**：Pipeline 分析师
**触发**：用户提供任何形式的输入

**执行**：
1. 解析所有输入内容（会议记录、对话、文档、截图等）
2. 提取明确需求、隐含需求、约束条件
3. 识别缺口：不清晰、不充分、有矛盾的地方
4. 初始化 `docs/solution-context.json`
5. 生成第一轮澄清文档 `docs/clarification/round-1.md`

**输出格式**：
```
## 我的理解
[对输入内容的理解摘要]

## 已提取的需求
- [明确需求列表]

## 发现的缺口
- [不清晰/不充分/有矛盾的地方]

## 当前完整度评估：XX/100

---
📄 已生成第一轮澄清文档（docs/clarification/round-1.md）
请将该文档转发给相关方确认，把答案带回来。
```

---

### Phase 2 — 澄清循环
**角色**：Pipeline 分析师
**触发**：用户带回上游确认结果
**循环条件**：Solution_Context 完整度 < 80 或仍有未确认的关键问题

**执行**：
1. 将确认结果更新到 Solution_Context
2. 重新评估完整度
3. 识别新产生的缺口
4. 如完整度 < 80：生成下一轮澄清文档
5. 如完整度 ≥ 80：生成完整度报告，提示可进入阶段二

**澄清文档质量标准**（INV-008）：

澄清文档必须包含以下六个要素，确保上游需求方无需追问即可直接回复：

```markdown
# 澄清文档 — 第 N 轮
> 项目：[项目名] | 日期：[日期] | 发起方：[你的角色]

## 背景说明
[让对方理解为什么需要确认这些问题，2-3句话]

## 需要确认的问题

### 问题 1：[简短标题]
**背景**：[为什么需要确认这个]
**问题**：[具体、无歧义的问题描述]
**影响**：[不确认会导致什么问题]
**可选方案**：
- 方案 A：[描述] — 适用场景：[...]
- 方案 B：[描述] — 适用场景：[...]
**期望回复**：请选择方案 A 或 B，或提供其他方案

### 问题 2：...

## 期望回复格式
请针对每个问题编号回复，例如：
- 问题1：选方案A，原因是...
- 问题2：...

## 期望回复时间
[建议截止时间]
```

## 阶段二：确认后产出

### Phase 3 — 生成结构化开发资产
**角色**：产品经理
**触发**：Solution_Context 完整度 ≥ 80，用户确认进入阶段二

**输出**（全部基于 Solution_Context，不引入未确认假设）：

| 文档 | 路径 | 内容 |
|------|------|------|
| 需求规格 | `docs/requirements.md` | 功能需求、验收标准、优先级 |
| 接口契约 | `docs/interface-contract.md` | API 定义、请求/响应格式、错误码 |
| 数据模型 | `docs/data-model.md` | 实体定义、字段、关系、约束 |
| 测试数据 | `docs/test-data.md` | 正常场景、边界场景、异常场景的测试数据 |

---

### Phase 4 — 技术设计
**角色**：架构师
**触发**：开发资产确认

**输出**：`docs/design.md`、`docs/project.md`

**部署前检查清单**（必须完成）：
- [ ] 读取所有配置文件（nginx.conf、.env、systemd service 等）
- [ ] 识别 IP 白名单、硬编码路径、权限设置
- [ ] 确认端口占用
- [ ] 确认依赖版本兼容性

---

### Phase 5 — 开发实施（含持续支撑）
**角色**：全栈工程师
**触发**：技术设计确认

**开发阶段持续支撑**：
进入开发后，Pipeline 的澄清循环能力不停止。遇到以下场景时随时触发：
- 需求变更
- 文档缺口
- 逻辑说不通
- 需要协同方配合

触发后生成**面向协同方的沟通文档**，明确告诉对方"你需要怎么配合我"，格式同澄清文档质量标准。

---

### Phase 6 — 测试验收
**角色**：QA 工程师

**测试覆盖要求**：
- 单元测试覆盖率 ≥ 80%
- 所有 P0 功能必须有集成测试
- 必须测试异常场景：错误密码/凭证、空输入、越权访问、边界值

---

### Phase 7 — 运维部署
**角色**：DevOps 工程师

**部署验收必须包含**：
1. 所有页面/接口的 HTTP 状态码验证
2. 认证流程端到端：正确凭证 → token → 受保护接口
3. 错误场景：错误凭证被正确拒绝
4. 服务进程状态验证

**问题排查**：用户反馈 → 读取日志和配置 → 分析根本原因 → 修复 → 验证 → 汇报
