# 对抗性自检

## 目的

四维评分容易"主观虚高"。对抗性自检通过模拟不同视角，主动找产出物的问题。

## 五个对抗视角

### 1. 用户视角
**问**：实际用起来会遇到什么坑？

检查项：
- [ ] 操作步骤是否清晰？新手能跑通吗？
- [ ] 错误信息友好吗？
- [ ] 边界场景（空数据、超长输入、网络断开）会怎样？
- [ ] 文档与实际行为一致吗？

### 2. 对手/竞品视角
**问**：竞品/对手会从哪里攻击？

检查项：
- [ ] 哪些地方逻辑薄弱？
- [ ] 哪些假设不成立时方案崩盘？
- [ ] 成本/性能瓶颈在哪？
- [ ] 用户为什么可能选竞品？

### 3. 未来维护者视角
**问**：6 个月后接手的人会骂哪里？

检查项：
- [ ] 关键决策的理由记录了吗？
- [ ] 命名清晰吗？
- [ ] 复杂逻辑有注释吗？
- [ ] 测试覆盖了关键路径吗？

### 4. 新手视角
**问**：第一次接触的人哪里看不懂？

检查项：
- [ ] 专业术语首次出现时解释了吗？
- [ ] 缩写有展开吗？
- [ ] 假设的前置知识合理吗？
- [ ] 能从头到尾连贯读完吗？

### 5. 极端场景视角
**问**：流量 10 倍 / 数据 100 倍 / 时间紧到 1/10 时怎样？

检查项：
- [ ] 性能瓶颈？
- [ ] 容量上限？
- [ ] 单点故障？
- [ ] 关键路径过长？

## 输出格式

每个视角至少 1 条挑刺，总计至少 3 条：

```
## 对抗性自检发现

### 🔍 用户视角
- 问题：[具体描述]
- 严重度：高 / 中 / 低
- 建议：[改进方向]

### 🔍 对手视角
- 问题：...

### 🔍 维护者视角
- 问题：...

### 🔍 新手视角
- 问题：...

### 🔍 极端场景
- 问题：...

## 自检总结
- 已修复：N 项
- 已记录但未修复：N 项（写入 deliver 的"已知局限"）
- 严重度高的未修复：N 项（必须告知用户）
```

## 已修复 vs 已记录

### 已修复
- 在当前阶段就解决了
- 不影响交付

### 已记录但未修复
- 不阻塞当前交付
- 写入 deliver 的"已知局限"
- 用户知情后接受

### 严重度高未修复
- 必须降低 review 评分
- 主动告知用户
- 提供后续修复方案

## 触发时机

- 在 review skill 内部强制执行
- deliver 之前再做一次

## 不允许的情况

- ❌ 不做对抗性自检
- ❌ 找不到 3 条挑刺（说明不够认真）
- ❌ 把高严重度问题当作"已知局限"忽略
- ❌ 自检后不更新评分
