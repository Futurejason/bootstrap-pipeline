# 四维质量门规范

每个 skill 输出前必须自评 4 个维度。任一维度不达标 → 重做或降级。

## 1. 完备性（Completeness）

**核心问题**：是否覆盖了所有应该覆盖的内容？

### 检查清单
- [ ] 用户原始问题的所有点都回答了？
- [ ] 边界场景考虑了？（异常输入、极值、特殊条件）
- [ ] 失败处理路径有了？
- [ ] 必要的依赖、前置条件说明了？
- [ ] 关键约束都明确了？

### 评分公式
```
score = (覆盖项 / 总要求项) × 10
```

### 通过线
- 默认：≥ 8
- L3 完整级：≥ 9
- L1 简单问答：≥ 7

### 失败处理
- 评分 < 通过线 → 列出缺失项 → 补充 → 重评

## 2. 准确性（Accuracy）

**核心问题**：内容是否真实、有依据？

### 检查清单
- [ ] 关键论断有证据链（论据/来源/可信度）？
- [ ] 数字/数据来源真实？
- [ ] 代码逻辑能跑通？
- [ ] 引用的文档/法规可查？
- [ ] 没有事实性错误？

### 评分公式
```
score = (有证据论断 / 总论断) × 10 - (事实错误数 × 2)
```

### 通过线
- 默认：≥ 8
- 涉及法律/医疗/财务：≥ 9（更严格）

### 失败处理
- 缺证据 → 补证据链
- 有错误 → 修正 → 标注修正过程

## 3. 一致性（Consistency）

**核心问题**：是否前后矛盾、与上下文一致？

### 检查清单
- [ ] 与上游 skill 的输出一致？
- [ ] 内部不矛盾（论断 A 与论断 B 不冲突）？
- [ ] 术语统一（同一概念用同一名称）？
- [ ] 风格统一（语调、格式）？
- [ ] 与用户已确认的决策一致？

### 评分公式
```
score = (一致项 / 总检查项) × 10
```

### 通过线
- 默认：≥ 7
- 跨多模块项目：≥ 8

### 失败处理
- 矛盾点 → 列出 → 修复 → 重评

## 4. 可行性（Feasibility）

**核心问题**：方案是否能在约束内执行？

### 检查清单
- [ ] 在时间/预算/资源约束内？
- [ ] 技术栈/工具用户掌握或能学会？
- [ ] 步骤具体可操作（不是"应该做..."）？
- [ ] 风险有应对策略？
- [ ] 依赖关系清楚？

### 评分公式
```
score = (可行项 / 总检查项) × 10
```

### 通过线
- 默认：≥ 7
- 涉及部署/上线：≥ 9

### 失败处理
- 不可行项 → 调整方案或上报阻塞

## 综合判定

```
通过：4 维都 ≥ 通过线
警告：任一维度 < 通过线但差距 ≤ 2
失败：任一维度 < 通过线且差距 > 2
```

### 警告处理
- 进入下一阶段，但在 deliver 中标注关注点
- review 输出 status: PASSED_WITH_NOTES

### 失败处理（执行降级阶梯）
1. 第 1 次失败：返回上一 skill 重做
2. 第 2 次失败：调整方案（可能回 plan）
3. 第 3 次失败：DOWNGRADE 简化交付 + 上报

## 自评模板

```yaml
quality_score:
  completeness:
    score: 9
    pass_line: 8
    status: ✅
    notes: "缺少错误处理示例"
  accuracy:
    score: 8
    pass_line: 8
    status: ✅
    notes: "1 处证据链不完整"
  consistency:
    score: 9
    pass_line: 7
    status: ✅
  feasibility:
    score: 8
    pass_line: 7
    status: ✅
overall: PASSED | PASSED_WITH_NOTES | FAILED
```

## 对抗性自检（可选但推荐）

通过四维评分后再做一次对抗性自检：
- 用户视角：用起来会遇到什么坑？
- 对手视角：会从哪里攻击？
- 维护者视角：6 个月后看会骂哪里？
- 新手视角：哪里看不懂？

至少识别 3 条挑刺，写进 deliver 的"已知局限"。
